¿El pedido debe esperar al correo?

Hoy: todo en una solicitud

Validar stock → confirmar → notificar → responder.

Un servicio lento alarga la espera del cliente.

Necesidad del negocio

Al confirmar un pedido, normalmente se notifica al cliente como parte de la experiencia.

Confirmar ahora y procesar esa notificación después, incluso si el consumidor está detenido.

PRODUCTOR · A3

Dos confirmaciones diferentes

// Fragmento del productor: canal de confirmación ya creado.
channel.publish('pedidos.exchange', 'pedido.confirmado',
  Buffer.from(JSON.stringify(evento)),
  { persistent: true, contentType: 'application/json' });
await channel.waitForConfirms();

Publisher confirm

El broker reconoce la publicación. Usar createConfirmChannel() y declarar primero la topología.

Ack del consumidor

El worker reconoce el procesamiento después de guardar. Ocurre en otro momento y en otro canal.

Un publisher confirm no demuestra que el worker haya procesado la notificación.

MODELO · A4

Confirmación y notificación se separan

// Campos que agregamos a models/Pedido.js
notificacionEstado: {
  type: String,
  enum: ['pendiente', 'procesada'],
  default: 'pendiente'
},
notificadoEn: { type: Date }

Estado del negocio

pendiente → confirmado
La confirmación conserva sus reglas y permisos.

Estado del efecto posterior

pendiente → procesada
El worker simula la notificación con una escritura. No envía correos reales.

WORKER · A4

Persistir primero, reconocer después

// Secuencia del consumidor (fragmento guiado).
try {
  const evento = JSON.parse(msg.content.toString());
  // Validar tipo, versión, UUID, fecha y data.pedidoId.
  // Buscar pedido confirmado y actualizar solo si está pendiente.
  // Guardar notificacionEstado='procesada' y notificadoEn.
  // Si ya está procesada, conservar el resultado anterior.
  channel.ack(msg);
} catch (error) {
  console.error('Notificación rechazada:', error.message);
  channel.nack(msg, false, false);
}

Consumir con noAck: false. Un mensaje inválido o pedido inexistente produce un error visible. Este rechazo descarta el mensaje: hoy no hay DLQ ni recuperación automática.

LÍMITE DEL DISEÑO · A6

La ventana que todavía no resolvimos

MongoDB
pedido confirmado ✓→Publicación
broker no disponible ✕→HTTP 503
consultar el pedido

Dos escrituras, sin atomicidad

El pedido puede quedar confirmado y su notificación pendiente, sin mensaje. No hay rollback ni reintento automático.

Idea para evolucionar: outbox

Guardar el hecho pendiente de publicar junto con el cambio del negocio; otro proceso lo publica. Requiere un diseño de consistencia y repetición.

No repetir la confirmación a ciegas. Consultar el estado y documentar el fallo. Resiliencia, retries y DLQ: Clase 05.

MICRODEMO 3 · O1

gRPC: un contrato para conversar

syntax = "proto3";
package pedidos;
service Pedidos {
  rpc ConsultarEstado (ConsultaPedido) returns (EstadoPedido);
}
message ConsultaPedido { string pedido_id = 1; }
message EstadoPedido {
  string estado = 1;
  string notificacion_estado = 2;
}

El archivo .proto define métodos y tipos. Esta llamada unaria también espera una respuesta. gRPC contempla streaming, pero no agrega una cola por sí mismo.

Lectura docente del contrato; no implementar servidor ni cliente gRPC en esta práctica.
