Trabajo Práctico Integrador

Diseñar e implementar una API integrada con persistencia, OAuth 2.0/JWT, scopes, asincronía, una integración adicional, observabilidad, pruebas y documentación reproducible.

Enunciado

El TPI integra las capacidades principales de la materia en una solución defendible y reproducible.

Objetivo

Construir una solución integrada

El equipo debe resolver un caso de negocio mediante una API REST con persistencia, seguridad OAuth 2.0/JWT, scopes, asincronía, una integración adicional, observabilidad, pruebas y documentación técnica.

Modalidad

Trabajo grupal

Equipos de 3 a 5 integrantes, un repositorio por equipo, elección de dominio registrada con la cátedra, dos entregas principales y defensa técnica presencial.

Alcance mínimo obligatorio

Estos puntos deben estar resueltos en la entrega final.

API
  • API REST sobre HTTP.
  • Recursos, métodos y códigos de estado correctos.
  • Contrato documentado: OpenAPI 3.1, colección HTTP o equivalente.
  • Al menos 8 endpoints relevantes.
Dominio
  • Persistencia en MongoDB, SQL u otra base aprobada.
  • Al menos 3 entidades de negocio.
  • CRUD de al menos 2 entidades.
  • Una transacción o flujo multi-paso de negocio.
Integración
  • Flujo asincrónico o diferido con efecto visible.
  • Integración adicional: Webhook, gRPC, WebSocket o equivalente aprobado.
  • Variables de entorno y .env.example.
  • Ejecución local reproducible.
Evidencia
  • Seguridad con OAuth 2.0/JWT y scopes.
  • Ejemplo mínimo de api_key.
  • Evidencias de pruebas y observabilidad.
  • README completo y defensa presencial con demo.

Seguridad requerida

La API debe validar identidad, permisos y configuración antes de ejecutar acciones sensibles.

Authorization Server

Auth0 o equivalente

Configurar una API, audience, issuer, scopes y un cliente Machine to Machine.

OAuth 2.0

client_credentials

Obtener access token desde el cliente y enviarlo como Bearer token a la API.

Resource Server

Validación JWT

Verificar firma, issuer, audience, expiración y scopes requeridos por endpoint.

Configuración requerida
  • Definir scopes según el dominio, por ejemplo read:pedidos, write:pedidos, confirm:pedidos, admin:productos.
  • Asignar permisos/scopes al cliente Machine to Machine.
  • Documentar en el README cómo configurar Auth0, qué scopes existen y cómo probar operaciones protegidas.
API key
  • Incluir un endpoint básico protegido con x-api-key.
  • Usarlo como comparación con OAuth 2.0/JWT, no como reemplazo del esquema principal.
  • No subir secretos reales al repositorio.

Checklist obligatorio del README

El README debe permitir que otra persona levante, pruebe y entienda el proyecto sin depender de explicaciones orales.

  • Proyecto, dominio elegido e integrantes.
  • Descripción del problema y alcance.
  • Arquitectura en un vistazo: diagrama C4 o link a docs/.
  • Requisitos previos.
  • Variables de entorno y explicación de .env.example.
  • Configuración de Auth0 o proveedor equivalente: API, audience, issuer, scopes, cliente Machine to Machine y permisos.
  • Cómo obtener un token con client_credentials.
  • Cómo probar endpoints protegidos con Bearer token.
  • Cómo probar el ejemplo con x-api-key.
  • Comandos para levantar localmente.
  • Cómo cargar datos iniciales.
  • Cómo ejecutar pruebas.
  • Cómo disparar el flujo asincrónico y dónde ver el efecto.
  • Cómo probar la integración elegida.
  • Cómo observar el sistema: logs, correlation ID, dashboard o métricas.
  • Endpoints principales y ejemplos de uso.
  • Decisiones técnicas principales o links a ADRs.
  • Limitaciones conocidas y mejoras futuras.
  • Tag/release y hash de commit de la entrega.

Dominio

1. Pedidos en restaurante

  • CRUD: productos y pedidos.
  • Flujo: confirmar pedido, calcular total, cambiar estado y generar orden de cocina.
  • Integración: WebSocket de cocina, Webhook de estado o gRPC a stock.
  • Scopes: `read:pedidos`, `write:pedidos`, `confirm:pedidos`, `admin:productos`.
Dominio

2. E-commerce

  • CRUD: productos y pedidos o carritos.
  • Flujo: confirmar compra con stock, total, pedido y pago simulado.
  • Integración: Webhook de pago, gRPC a stock o WebSocket de estado.
  • Scopes: `read:productos`, `write:productos`, `write:pedidos`, `confirm:compras`.
Dominio

3. Turnos de salud

  • CRUD: pacientes y turnos o profesionales.
  • Flujo: reservar turno validando disponibilidad y evitando solapamientos.
  • Integración: Webhook de confirmación, WebSocket de agenda o historia clínica simulada.
  • Scopes: `read:turnos`, `write:turnos`, `cancel:turnos`, `admin:profesionales`.
Dominio

4. Mesa de ayuda

  • CRUD: tickets y usuarios o agentes.
  • Flujo: escalar ticket validando prioridad, estado, responsable y SLA.
  • Integración: Webhook a canal externo, WebSocket de tablero o gRPC a usuarios.
  • Scopes: `read:tickets`, `write:tickets`, `assign:tickets`, `close:tickets`.
Dominio

5. Biblioteca digital

  • CRUD: títulos y usuarios o préstamos.
  • Flujo: prestar e-book validando cupo, usuario, vencimiento y espera.
  • Integración: WebSocket de lista de espera, Webhook a mailing o gRPC a catálogo.
  • Scopes: `read:titulos`, `write:titulos`, `read:prestamos`, `write:prestamos`.
Dominio

6. Eventos y entradas

  • CRUD: eventos y entradas o compras.
  • Flujo: comprar entrada validando disponibilidad, pago y emisión.
  • Integración: Webhook de pago, WebSocket de control de acceso o gRPC a validador.
  • Scopes: `read:eventos`, `write:eventos`, `buy:entradas`, `validate:entradas`.
Dominio

7. Alquiler de vehículos

  • CRUD: vehículos y reservas.
  • Flujo: confirmar reserva con disponibilidad, bloqueo, verificación y contrato.

  • Scopes: `read:vehiculos`, `write:vehiculos`, `read:reservas`, `confirm:reservas`.
Dominio

8. Salas de co-working

  • CRUD: salas y reservas.
  • Flujo: programar reserva validando disponibilidad, capacidad y recursos.
  • Integración: Webhook con calendario, WebSocket de ocupación o gRPC a recursos.
  • Scopes: `read:salas`, `write:salas`, `read:reservas`, `admin:recursos`.
